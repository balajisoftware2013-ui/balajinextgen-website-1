✓ FIX H: LineItems Persistence
   PROBLEM: reconcileDB() parsed lineItems from ITEMS_JSON but never attached 
            lineItems[] to recovered purchase/sale records. Reports needing item-
            level data (Stock Ledger, Item-wise Purchase/Sales) showed "—" for 
            quantities despite stock counts being correct.
   SOLUTION: Every healed purchase/sale record now includes lineItems[] array,
            identical to records never missing in the first place.
   STATUS: ✓ IMPLEMENTED in reconcileDB()

✓ FIX I: Real-Time Sheet Sync (Critical for Data Durability)
   PROBLEM: Google Sheets tabs (PURCHASES, SALES, CUSTOMERS, SUPPLIERS, ITEMS)
            were not kept in real-time sync with app's in-memory data. If 
            APP_DATA blob corrupted, there was no trustworthy recovery source.
   SOLUTION: New sync functions always called by frontend on every 
            add/edit/purchase/sale:
            - syncPurchaseRow() → PURCHASES tab
            - syncSaleRow() → SALES tab
            - syncCustomerRow() → CUSTOMERS tab
            - syncSupplierRow() → SUPPLIERS tab
            - syncItemRow() → ITEMS tab
            Each upserts-by-id (never erases), keeping sheets as durable 
            source of truth. If APP_DATA corrupts, reconcileDB() auto-heals
            from these tabs on next login.
   STATUS: ✓ IMPLEMENTED - frontend MUST call these on every transaction
   NEW ENDPOINTS:
     - SYNC_PURCHASE_ROW (req.sheetId, req.id, req.supp, req.date, req.total, req.mode, req.lineItems)
     - SYNC_SALE_ROW (req.sheetId, req.id, req.cust, req.date, req.total, req.mode, req.lineItems)
     - SYNC_CUSTOMER_ROW (req.sheetId, req.id, req.name, req.mobile, req.due, req.limit, req.lastDate)
     - SYNC_SUPPLIER_ROW (req.sheetId, req.id, req.name, req.mobile, req.due)
     - SYNC_ITEM_ROW (req.sheetId, req.id, req.name, req.unit, req.hsn, req.pRate, req.sRate, req.gst, req.stock, req.min)

✓ FIX J: Password Scoping & Hashing
   PROBLEM: v16 FIX G scoped hashAllPlaintextUserPasswords() and 
            hashAllPlaintextClientAdminPasswords() to BOS_INDUSTRIES only, but
            new passwords in registerClient() and login() could still be set 
            without guaranteeing salt-based hashing.
   SOLUTION: registerClient() now ALWAYS calls hashPass(password) with 
            per-user salt. Login upgrades legacy hashes silently.
            All passwords are now permanent-salt format or rejected.
   STATUS: ✓ IMPLEMENTED - registerClient() now always hashes with salt

✓ FIX K: Purchase & Sales Ledgers + Item-Wise Reports (Tally-Style)
   PROBLEM: Reports were totals-only; no transaction-by-transaction visibility
            with item details (Qty, Rate, GST). Users cannot match bills or
            see item-level movement like Tally does.
   SOLUTION: Four new report generators:
            1. generatePurchaseLedger(req) → all purchases + lineItems (date ordered)
            2. generateSalesLedger(req) → all sales + lineItems (date ordered)
            3. generateItemWisePurchase(req) → each item's purchase transactions
            4. generateItemWiseSales(req) → each item's sale transactions
            Each returns transaction-level detail, grouped appropriately, 
            with running totals. All support dateRange filtering.
   NEW ENDPOINTS:
     - GET_PURCHASE_LEDGER (req.sheetId, req.data, req.dateRange)
     - GET_SALES_LEDGER (req.sheetId, req.data, req.dateRange)
     - GET_ITEM_WISE_PURCHASE (req.sheetId, req.data, req.dateRange)
     - GET_ITEM_WISE_SALES (req.sheetId, req.data, req.dateRange)
   STATUS: ✓ IMPLEMENTED - frontend MUST implement report UI pages

✓ FIX L: Stock Ledger & Inventory Management
   PROBLEM: Users cannot see which purchases/sales affected each item's stock,
            or trace stock balance over time. Inventory reconciliation is blind.
   SOLUTION: Two new report generators:
            1. generateStockLedger(req) → every purchase/sale movement for each
               item, date-ordered with running balance
            2. generateStockSummary(req) → quick snapshot of current stock, min
               levels, status (LOW/OUT/OK)
   NEW ENDPOINTS:
     - GET_STOCK_LEDGER (req.sheetId, req.data, req.dateRange)
     - GET_STOCK_SUMMARY (req.sheetId, req.data)
   STATUS: ✓ IMPLEMENTED - frontend MUST implement Inventory > Stock Ledger page

✓ FIX M: Date Range Filtering for All Reports
   PROBLEM: Dashboard and reports cannot filter by month/quarter/FY. Users 
            see all-time totals with no period control.
   SOLUTION: filterTransactionsByDateRange() helper supports:
            - "TODAY" → current day
            - "MONTH" → current calendar month
            - "QUARTER" → current quarter
            - "HALF" → H1 or H2 of current year
            - "FY" → Indian FY (Apr 1 - Mar 31)
            - "YYYY-MM-DD-YYYY-MM-DD" → custom date range
   All report generators accept req.dateRange parameter.
   STATUS: ✓ IMPLEMENTED - frontend MUST pass dateRange to all report calls

FRONTEND (HTML) — Critical Changes Required

The original balaji-business-os.html (11006 lines) requires these key changes:

1. SYNC CALLS ON EVERY TRANSACTION (Critical for FIX I)
   ─────────────────────────────────────────────────────
   When user ADDS/EDITS a purchase, call:
     POST request to 'SYNC_PURCHASE_ROW' with full transaction details
   When user ADDS/EDITS a sale, call:
     POST request to 'SYNC_SALE_ROW' with full transaction details
   When user ADDS/EDITS a customer, call:
     POST request to 'SYNC_CUSTOMER_ROW' with full customer details
   When user ADDS/EDITS a supplier, call:
     POST request to 'SYNC_SUPPLIER_ROW' with full supplier details
   When user ADDS/EDITS an item, call:
     POST request to 'SYNC_ITEM_ROW' with full item details

   These must happen BEFORE saving to APP_DATA, so if DB_JSON ever corrupts,
   the sheet tabs still have the complete history.

2. LEDGER PAGES (FIX K — Purchase/Sales/Item-Wise Reports)
   ─────────────────────────────────────────────────────────
   Add new pages to the app:
   
   a) Purchase Ledger (/purchase-ledger)
      - Load all purchases via GET_PURCHASE_LEDGER
      - Show bill-by-bill (date, bill#, supplier, total, mode)
      - Expand each row to show lineItems (qty, rate, GST, amount)
      - Date range filter (month/quarter/FY selector)
      - Total row showing sum of period
   
   b) Sales Ledger (/sales-ledger)
      - Same structure as purchase ledger
      - Group by customer instead of supplier
      - Date range filter
   
   c) Item-wise Purchase Report (/item-purchase)
      - One section per item
      - Show each purchase transaction for that item (qty, rate, amount)
      - Summary: total qty purchased, total amount, average rate in period
      - Date range filter
   
   d) Item-wise Sales Report (/item-sales)
      - One section per item
      - Show each sale transaction for that item (qty, rate, amount)
      - Summary: total qty sold, total amount, average rate in period
      - Date range filter

3. STOCK LEDGER PAGE (FIX L — Inventory Movements)
   ────────────────────────────────────────────────
   Add new page: Inventory > Stock Ledger (/stock-ledger)
   
   - One section per item (especially those with movements in period)
   - Show opening stock + all movements (purchases +qty, sales -qty)
   - Each row: date, type (Purchase/Sale), bill#, party, qty, rate, amount
   - Running balance column showing stock after each transaction
   - Closing stock row
   - Date range filter
   
   Add new page: Inventory > Stock Summary (/stock-summary)
   - Quick table: Item | Current Stock | Min Level | Status | Purchase Rate

4. DASHBOARD DATE FILTERING (FIX M — Period Selection)

   - Display period label on all reports
   
   Example: "Month: Apr 2024" or "FY: 2024-25 (Apr 2024 - Mar 2025)"

5. PASSWORD HANDLING (FIX J — Already Secure in Backend)
   ───────────────────────────────────────────────────────
   No frontend changes needed — backend now guarantees all new passwords

DEPLOYMENT NOTES
═══════════════════════════════════════════════════════════════════════════════

1. BACKWARD COMPATIBILITY
   - All v17 changes are backward-compatible with existing data
   - Existing clients can still login and use app unchanged
   - New sync functions do not interfere with existing saves
   - Ledger & report endpoints won't break if dateRange param missing (defaults to all-time)

2. PERFORMANCE IMPACT
   - Sync functions add ~500ms per transaction (minimal)
   - Report generation is O(n) transactions, ~1-2s for typical client
   - Date filtering is O(n) — no indexes needed (data is small)
   - Reconciliation healing is one-time, subsequent logins are fast

3. DATA MIGRATION
   - NO migration script needed — existing APP_DATA compatible with v17
   - On first login after v17 deploy, reconcileDB() will auto-heal masters
     from sheet tabs using new markers in APP_DATA!F1/G1/H1
   - PURCHASES/SALES lineItems may be missing for old bills (see v13 limitation)
     but can be recovered if ITEMS_JSON column exists (v13+)

4. ERROR HANDLING
   - If sync fails (network), transaction still saves to app locally
   - Sync retry on next save (same transaction sent again)
   - Reconcile runs on every login to catch any gaps
   - All errors logged to ERROR_LOG sheet with timestamp
